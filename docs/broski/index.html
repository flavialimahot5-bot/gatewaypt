Documentação Broski

Receba por MB WAY e Multibanco no seu negócio em Portugal, com uma API simples em https://api.broski.pt.

Introdução

A integração completa tem 4 passos:

  1. Ative a sua conta no painel (app.broski.pt) — verificação de dados e documento.
  2. Gere a sua chave secreta em Configurações → API.
  3. Crie pedidos com POST /v1/orders — MB WAY confirma em segundos; Multibanco emite um voucher pago em até alguns dias.
  4. Receba webhooks com a confirmação de cada pagamento e libere o produto/serviço.

Convenções: valores sempre em cêntimos (€19,90 = 1990); moeda EUR; respostas JSON com datas RFC 3339 (UTC); a API é versionada no path (/v1) e evolui de forma aditiva — campos novos podem aparecer, os existentes não mudam de significado.

Integre com IA — prompt pronto

Vai integrar usando um assistente de código (Claude, ChatGPT, Copilot…)? Clique em Copiar no canto do bloco e cole junto do seu pedido — ele contém tudo que a IA precisa saber sobre a nossa API, incluindo o payload real dos nossos webhooks, sem ela precisar navegar nas docs. Você também pode anexar o openapi.yaml.

## API Broski (gateway de pagamentos, Portugal, EUR)
Base URL: https://api.broski.pt
Autenticação: header "Authorization: Bearer sk_live_..." em toda chamada.
A chave fica SOMENTE no servidor (variável de ambiente) — nunca em browser,
app móvel ou repositório. TODA chamada à API parte do SEU backend: a API
rejeita chamadas de browser (CORS restrito, de propósito) — não existe
NENHUMA chamada client-side, nem para consultar status.
Valores sempre em CÊNTIMOS (número JSON inteiro): €19,90 = 1990 — nunca
string ("1990") nem decimal (19.90). Moeda única: EUR.
Envie SOMENTE os campos documentados — campo desconhecido causa 400.
Envie o corpo SEMPRE em UTF-8, com "Content-Type: application/json;
charset=utf-8". Byte fora de UTF-8 responde 400 invalid_encoding e a
requisição é recusada inteira — nada é gravado. Se os dados vierem de
sistema legado (Latin-1/CP1252), converta ANTES de serializar o JSON:
acentos mal codificados não são recusados por acaso, são recusados sempre.

FLUXO 100% SERVER-SIDE: NÃO existe SDK JavaScript, biblioteca de cliente,
client_secret, publishable key, iframe/Elements, página de pagamento
hospedada, modal, nem redirect. NÃO carregue nenhum script de terceiros no
checkout. O SEU backend chama a API REST e o SEU checkout renderiza a
resposta JSON (instruções MB WAY ou voucher Multibanco). A única credencial
é a sk_live_ do servidor.

## Fluxo ponta-a-ponta (siga esta sequência)
1. Browser envia o carrinho ao SEU servidor.
2. SEU servidor calcula o amount (nunca confie no browser) e faz o
   POST /v1/orders.
3. SEU servidor devolve ao browser SÓ o necessário: {id, status, multibanco?}.
4. Checkout renderiza: MB WAY → tela de espera; Multibanco → voucher.
5. Webhook order.paid chega ao SEU servidor → atualiza o pedido → libera.
6. O browser acompanha consultando O SEU servidor (nunca a API Broski).

## Criar pedido — POST /v1/orders
Headers: Authorization, Content-Type: application/json e
Idempotency-Key (OBRIGATÓRIO, 1–128 chars — derive do id do pedido da loja,
ex.: "pedido-1042-v1"). Reenvio com a mesma chave e mesmo corpo devolve a
resposta original (header Idempotent-Replay: true); mesma chave com corpo
diferente responde 409 idempotency_key_reused.
A chave identifica UMA tentativa com UM corpo exato: se QUALQUER campo mudar
(valor, método, telefone), gere chave nova incrementando o sufixo
("pedido-1042-v2"). Reuse a mesma chave SOMENTE para reenviar a MESMA
requisição após timeout/erro de rede.

Corpo (JSON):
- amount      int    obrigatório. MB WAY: 50–500000 (€0,50–€5.000).
                     Multibanco: 1–100000000 (na prática o mínimo é a
                     tarifa da conta — abaixo → 400 amount_below_fee).
                     Cada conta tem um VALOR MÁXIMO POR PEDIDO, definido
                     para a conta; acima → 400 amount_above_limit.
- currency    string opcional; se enviar, exatamente "EUR" (maiúsculo).
                     Recomendado: omitir.
- method      string obrigatório: "mbway" | "multibanco".
- phone       string obrigatório se mbway. Telemóvel PT "+3519XXXXXXXX"
                     (2º dígito 1/2/3/6). Normalize no SEU servidor: remova
                     espaços e prefixe +351 se o cliente digitar só os 9
                     dígitos. Espaços são tolerados.
- external_reference string obrigatório, ÚNICO por conta (A-Za-z0-9_-. até
                     128). Duplicado responde 409 external_reference_taken.
- description string opcional (≤140) — nome do produto (aparece no painel
                     do lojista; não volta nas respostas da API).
- checkout_url string OBRIGATÓRIO (≤1024) — URL http(s) da página de checkout
                     onde a venda ocorreu. SEMPRE envie. Fica registrada no
                     pedido (uso interno); não volta nas respostas da API.
- product_type string opcional: "digital" (padrão) | "physical". Em
                     "physical" o customer.address vira OBRIGATÓRIO.
- customer    objeto OBRIGATÓRIO: {name, email, phone, nif, address}.
                     customer.email é OBRIGATÓRIO e validado: ausente ou
                     mal formado responde 400 email_required. É a chave do
                     cadastro de clientes — pedidos com o mesmo e-mail são o
                     mesmo cliente. name, phone e nif são opcionais.
                     Armazenado cifrado; o endereço só aparece no painel do
                     lojista (nunca na API pública).
- customer.address objeto opcional (OBRIGATÓRIO se product_type=physical):
                     {line1 (obrig.), line2 (opc.), postal_code (obrig.; PT
                     NNNN-NNN), city (obrig.), region (opc.), country (ISO-2,
                     padrão PT)}. Enviar o objeto exige line1+postal_code+city;
                     parcial → 400.

Resposta 201 (MB WAY):
{"id":"ord_...","status":"pending","amount":1990,"currency":"EUR",
 "method":"mbway","product_type":"digital","external_reference":"...",
 "livemode":true,"created_at":"RFC3339"}
O cliente aprova no app MB WAY; a confirmação chega EM SEGUNDOS via webhook.
A resposta MB WAY NÃO tem campo de prazo: a janela de aprovação é curta
(poucos minutos); o desfecho não-pago chega como order.failed OU
order.expired — trate os dois como terminal não-pago idênticos.

## Espera do MB WAY no checkout (padrão OBRIGATÓRIO)
Após o 201, mostre "Confirme o pagamento no app MB WAY do seu telemóvel"
com indicador de espera. O browser consulta O SEU servidor (polling de um
endpoint SEU a cada 2–3 s, ou SSE/WebSocket), e o seu servidor responde com
o status que recebeu do webhook. NUNCA faça polling do GET /v1/orders/{id}
da Broski por checkout — o limite de 120 req/min é por chave, GLOBAL
(compartilhado com a criação de pedidos): meia dúzia de clientes em espera
derrubaria a loja inteira em 429. Use o GET no máximo como fallback pontual
(1 consulta se o webhook não chegou em ~60 s). Timeout de UX: após ~5 min
sem confirmação, ou ao receber order.failed/order.expired, mostre "pagamento
não confirmado" + botão de tentar de novo (ver regras de retry abaixo).

Resposta 201 (Multibanco):
{... "status":"awaiting_payment",
 "multibanco":{"entity":"11249","reference":"123 456 789",
               "amount":4990,"expires_at":"RFC3339"}}
REGRAS MULTIBANCO: exiba entidade, referência, valor e prazo (expires_at —
não assuma um número fixo de dias) ao cliente. "awaiting_payment" é estado
NORMAL e duradouro — não trate como erro nem crie pedido novo. O checkout
NÃO espera o pagamento: mostre o voucher numa tela FINAL ("guarde estes
dados"), envie-o também por email da SUA loja (a Broski não envia email ao
cliente final) e ENCERRE o fluxo — sem spinner, sem polling. A confirmação
chega em horas/dias via order.paid; só então libere o produto. Passado o
expires_at, esconda o voucher e ofereça gerar novo pedido (o order.expired
pode chegar com atraso em relação ao expires_at).

Erros possíveis: 400 validation_failed | invalid_json |
currency_not_supported | amount_below_fee | amount_above_limit
(ver "Limite por pedido" abaixo) | payment_method_unavailable (ver
"Método indisponível" abaixo); 401 unauthorized;
402 payment_failed (pedido desfeito — pode reusar a external_reference);
402 mbway_not_active_for_phone (o número informado não tem MB WAY ativo —
pedido desfeito; ver "Número sem MB WAY" abaixo);
409 (acima); 409 mbway_pending_for_phone e 409 mbway_temporarily_blocked
(ver "Bloqueio por telemóvel" abaixo — em ambos NADA foi criado; pode
reenviar a MESMA external_reference e Idempotency-Key depois);
413 body_too_large (>64KB); 429 rate_limited
(120 req/min por chave, global — implemente backoff exponencial; o 429 NÃO
traz Retry-After; os dois 409 de telemóvel trazem).
Envelope de erro:
{"error":{"type","code","message","param?","retry_after_seconds?"}}
(message em PT-BR, escrita para poder ser mostrada ao cliente final).

## Método indisponível
Uma conta pode não ter um dos métodos de pagamento disponível. Um pedido por
esse método é recusado antes de qualquer cobrança:
  HTTP 400  {"error":{"type":"invalid_request","code":"payment_method_unavailable",
   "param":"method",
   "message":"Este método de pagamento não está disponível. Escolha outro método de pagamento."}}
Nada foi criado (nem pedido, nem cobrança) e, no MB WAY, o telemóvel não fica
bloqueado. Repetir o MESMO pedido dá o mesmo resultado: ofereça o outro método
ao cliente. Pode reusar a mesma external_reference com o outro método.

## Limite por pedido
Cada conta tem um valor máximo por pedido. Um pedido acima dele é recusado
antes de qualquer cobrança:
  HTTP 400  {"error":{"type":"invalid_request","code":"amount_above_limit",
   "param":"amount",
   "message":"O valor deste pedido excede o limite permitido."}}
A resposta diz APENAS que o valor passou do limite — ela NÃO informa qual é o
limite. O titular da conta consulta o valor no painel, em Saldo →
"Informações úteis".
O que fazer no seu checkout:
  - MOSTRE a "message" tal e qual ao cliente e deixe-o reduzir o pedido.
    Não invente um valor de limite na mensagem: a API não o envia.
  - Nada foi criado: ao reenviar com um valor menor pode reusar a MESMA
    external_reference.
  - Se quiser validar o carrinho antes de enviar, peça o valor ao titular da
    conta (ele vê no painel) e guarde-o como CONFIGURAÇÃO da integração —
    nunca fixo no código, porque pode ser alterado para a conta.
  - Não divida a compra em vários pedidos por conta própria para contornar o
    limite, e não faça retry automático: o resultado é o mesmo.
  - Para aumentar o limite, o titular da conta fala com o suporte.

## Número sem MB WAY
Se o telemóvel informado não tiver MB WAY ativo, a criação devolve:
  HTTP 402  {"error":{"type":"payment_error",
   "code":"mbway_not_active_for_phone","param":"phone",
   "message":"Este número de telemóvel não tem MB WAY ativo. Confira o número
   ou use outro método de pagamento."}}
O que fazer no seu checkout:
  - MOSTRE a "message" tal e qual ao cliente, junto ao campo do telemóvel.
  - Deixe-o CORRIGIR o número ou escolher Multibanco. Mantenha o resto do
    formulário preenchido.
  - NÃO reenvie o mesmo pedido com o mesmo número: o resultado é o mesmo.
    Não é falha temporária nem indisponibilidade — não faça retry automático.
  - O pedido foi desfeito: quando o cliente corrigir, pode reusar a MESMA
    external_reference e Idempotency-Key.
  - Não é possível saber de antemão se um número tem MB WAY; trate este erro
    como parte normal do fluxo, não como exceção.

## Bloqueio por telemóvel (MB WAY) — "um telemóvel, um pedido de cada vez"
Enquanto um pedido MB WAY está à espera de confirmação no app do cliente,
o MESMO número de telemóvel não consegue iniciar outro pedido MB WAY — em
NENHUMA loja da Broski (o bloqueio é global). A tentativa devolve:
  HTTP 409  {"error":{"type":"conflict","code":"mbway_pending_for_phone",
   "message":"Já existe um pagamento MB WAY à espera de confirmação para este
   número de telemóvel. Abra o app MB WAY e confirme (ou recuse) esse
   pagamento antes de iniciar outro. Se preferir, aguarde 4 minutos e tente
   de novo.","retry_after_seconds":240}}   + header Retry-After: 240
Há um SEGUNDO código, para um número temporariamente impedido de iniciar
pagamentos MB WAY (não há nenhum pagamento à espera de confirmação):
  HTTP 409  {"error":{"type":"conflict","code":"mbway_temporarily_blocked",
   "message":"Não é possível iniciar um pagamento MB WAY com este número de
   telemóvel neste momento. Tente novamente mais tarde ou use outro método de
   pagamento.","retry_after_seconds":10800}}  + header Retry-After: 10800
Trate os dois da MESMA forma; muda só o texto (que vem pronto) e o tempo de
espera, que pode ser de horas — por isso ofereça Multibanco como alternativa.
O que fazer no seu checkout:
  - MOSTRE a "message" tal e qual ao cliente (já está escrita para ele);
    NÃO trate como falha do pagamento nem crie outro pedido.
  - O bloqueio cai no instante em que o cliente confirma ou recusa o push
    no app (ou expira, no máximo em ~5 min). Pode reenviar EXATAMENTE o
    mesmo POST (mesma external_reference e Idempotency-Key) depois de
    retry_after_seconds — nada foi criado da primeira vez.
  - Se o cliente pagou o pedido anterior, ele vai receber o order.paid
    desse pedido; não abra um novo.
Só MB WAY tem este bloqueio (Multibanco não).

## Consultar — GET /v1/orders/{id}    (404 resource_not_found se não existir)
## Listar — GET /v1/orders?status=&method=&starting_after=  (25/página,
   {"data":[resumo...],"has_more":bool})
## Estornar — POST /v1/orders/{id}/refunds
   Corpo JSON OBRIGATÓRIO: {} = estorno total do restante;
   {"amount":int,"reason"?:str} = parcial (amount 0 ou ausente = total).
   Header Idempotency-Key OBRIGATÓRIO (1–128): reenvio com a MESMA chave
   devolve o estorno original — um retry NUNCA estorna duas vezes. Para um
   segundo estorno intencional, use uma chave NOVA.
   201 {"id":"ref_...","amount":n,"status":"succeeded"}.
   Erros: 409 order_not_paid; 400 refund_exceeds_amount;
   409 refund_failed (a chave já foi usada num estorno que falhou — use outra);
   409 refund_pending_review (o estorno foi recebido e está em análise — NÃO
   reenvie nem troque a chave: o resultado será confirmado).

## Status de um pedido (lista fechada)
pending          criado, aguardando o cliente confirmar (MB WAY).
awaiting_payment voucher emitido, aguardando pagamento (Multibanco).
                 Estado normal e duradouro — pode durar dias.
paid             pago e confirmado. ÚNICO status que libera a entrega.
expired          prazo esgotado sem pagamento. Terminal.
failed           não concluído ou recusado. Terminal.
refunded         estornado por INTEIRO. Terminal.
Não existe outro valor. Status fora desta lista: trate como desconhecido e
NÃO libere nada.

ESTORNO PARCIAL NÃO MUDA O STATUS E NÃO GERA WEBHOOK. O pedido continua
"paid" e só amount_refunded aumenta; order.refunded chega apenas quando o
estorno atinge o valor total. Concilie SEMPRE por amount - amount_refunded,
nunca só pelo status — um pedido "paid" com amount_refunded > 0 já teve
dinheiro devolvido. Para detectar estorno parcial, consulte
GET /v1/orders/{id}; ele não chega sozinho.

## Webhooks (OBRIGATÓRIO implementar — Multibanco confirma dias depois)
O lojista cadastra a URL HTTPS no painel Broski (Configurações → Webhooks) e
guarda o segredo "whbroski_..." (consultável depois em Configurações →
Webhooks → Ver segredo). Implemente um endpoint POST público que:
1. Lê o corpo CRU (bytes, antes de parsear JSON).
2. Verifica o header "Broski-Signature: t=<unix>,v1=<hex>" assim:
   esperado = HMAC-SHA256(secret, t + "." + corpo_cru) em hex;
   compare com v1 em TEMPO CONSTANTE; rejeite se |agora - t| > 300s.
   VETOR DE TESTE (sua implementação deve reproduzir):
   secret: whbroski_vetor_de_teste_nao_usar_em_producao
   t: 1750000000
   corpo: {"id":"evt_teste123","type":"order.paid","created":1750000000,"data":{"object":{"id":"ord_teste123","status":"paid"}}}
   header esperado: t=1750000000,v1=5fb448226598b14dea45ff94ee317c2c1edd464f87cd720b0d8673ea89731d4c
3. Responde 2xx em até 10s (processe assíncrono se precisar).
4. Deduplica pelo "id" do evento (entrega at-least-once, SEM ordem
   garantida) e confia no "status" do objeto, não no tipo do evento.

Envelope do evento (exemplo REAL de order.paid, MB WAY — ILUSTRATIVO, não
assinado; a ordem das chaves no JSON não é significativa, não parseie por
posição; para validar sua verificação use o VETOR DE TESTE acima):
{"id":"evt_7Kq2p9mXvA","type":"order.paid","created":1784469809,
 "data":{"object":{"object":"order","id":"ord_9f2c1ab34d","status":"paid",
   "amount":1990,"amount_refunded":0,"currency":"EUR","method":"mbway",
   "product_type":"digital","external_reference":"pedido-1042",
   "livemode":true,"created_at":"2026-07-19T14:03:11Z",
   "paid_at":"2026-07-19T14:03:29Z"}}}
data.object é o MESMO objeto do GET /v1/orders/{id} (inclui product_type e
amount_refunded; paid_at quando pago; multibanco quando há voucher).
Eventos: order.awaiting_payment, order.paid, order.failed, order.expired,
order.refunded (estorno TOTAL), payout.paid, dispute.created. O shape de
data.object segue data.object.object ("order" | "payout" | "dispute"):
- payout.paid  → {"object":"payout","id":"pay_...","amount":48000,
    "currency":"EUR","status":"paid","requested_at":"RFC3339","paid_at":"RFC3339"}
- dispute.created → {"object":"dispute","id":"dsp_...","order":"ord_...",
    "amount":1990,"currency":"EUR","reason":"...","status":"needs_response",
    "evidence_due_by":"RFC3339","created_at":"RFC3339"}
Seu endpoint pode receber tipos ALÉM destes — responda 2xx e ignore
qualquer type que não tratar; NUNCA falhe por tipo desconhecido;
ignore campos que não conhecer (novos podem surgir).
Webhooks são emitidos APENAS para pagamentos reais (livemode) — pagamentos
de teste não disparam webhook; teste o handler com o exemplo assinado acima.
Sem 2xx: retries por ~24h, depois dead-letter (reenvio manual no painel).
Redirecionamentos (3xx) contam como falha — cadastre a URL FINAL exata
(com/sem www importa); a URL pode ser editada no painel sem trocar o segredo.

## Regras de negócio INEGOCIÁVEIS
1. Libere o produto/serviço SOMENTE ao receber order.paid (nunca na criação
   do pedido, nunca confiando no browser do cliente).
2. O valor cobrado vem do SEU servidor — nunca aceite amount do cliente.
3. Trate order.failed/order.expired com mensagem clara e botão de tentar
   de novo. NOVA tentativa após failed/expired = pedido NOVO: gere
   external_reference NOVA (ex.: "pedido-1042-t2" — a anterior fica ocupada
   para sempre) E Idempotency-Key NOVA (ex.: "pedido-1042-v2"). Repetir a
   mesma chave devolve o pedido antigo já morto (replay), não cria outro.
   EXCEÇÃO: após um 402 (payment_failed ou mbway_not_active_for_phone) pode
   reusar a MESMA referência e chave (o pedido é desfeito).
4. Guarde o "id" (ord_...) retornado e associe ao pedido da sua loja.
5. Não há endpoint de webhook via API — o cadastro é no painel.
6. Os 409 de telemóvel NÃO são erro de pagamento e NUNCA se resolvem
   repetindo o pedido:
   - mbway_pending_for_phone: o cliente já tem um push MB WAY vivo (aqui ou
     noutra loja). Mostre a message e deixe-o decidir no app.
   - mbway_temporarily_blocked: o número está temporariamente impedido.
     Mostre a message, respeite retry_after_seconds (pode ser horas) e
     ofereça Multibanco.
   Em ambos: nada foi criado, não mude o telemóvel por sua conta e nunca
   crie outro pedido para "forçar".
7. 402 mbway_not_active_for_phone: o número não tem MB WAY. Mostre a message
   no campo do telemóvel e deixe o cliente corrigir ou usar Multibanco.
   Nunca repita o pedido com o mesmo número.
8. 400 amount_above_limit: o total passa o valor máximo por pedido da conta.
   A resposta NÃO traz o valor do limite — mostre a message tal e qual, sem
   acrescentar números. Nunca parta a compra em vários pedidos nem repita a
   tentativa.
9. 400 payment_method_unavailable: a conta não vende por esse método. Mostre
   a message e ofereça o OUTRO método (mbway ↔ multibanco). Nunca repita o
   pedido com o mesmo método, e não trate como falha temporária.

Autenticação

A API é exclusivamente servidor→servidor: chamadas de browser são bloqueadas por CORS de propósito — além de nunca expor a chave, nem consulta de status é client-side. Toda chamada leva Authorization: Bearer sk_live_…. A chave é criada no painel (até 10 ativas por conta — use uma por sistema e dê nomes: "Loja", "ERP"), exibida uma única vez, e pode ser revogada a qualquer momento.

Nunca use a chave no navegador, em apps móveis ou em repositórios. Ela pertence ao seu servidor. Chave exposta? Revogue no painel e gere outra — efeito imediato.

Primeiro pagamento

MB WAY — confirmação em segundos

curl https://api.broski.pt/v1/orders \
  -H "Authorization: Bearer sk_live_..." \
  -H "Idempotency-Key: pedido-1042-v1" \
  -H "Content-Type: application/json" \
  -d '{"amount":1990,"method":"mbway","phone":"+351912345678",
       "external_reference":"pedido-1042","description":"Curso de tráfego",
       "checkout_url":"https://sualoja.pt/checkout/curso-de-trafego",
       "customer":{"name":"Ana Cliente","email":"[email protected]"}}'

Resposta 201 com "status":"pending": o cliente recebe a notificação no app MB WAY e aprova. Em segundos chega o webhook order.paid (ou order.failed/order.expired). Limites MB WAY: €0,50 a €5.000 por pedido; telemóvel PT (+3519…) obrigatório.

Multibanco — voucher pago em dias

Mesma chamada com "method":"multibanco" (sem phone). A resposta 201 já vem "status":"awaiting_payment" com o voucher:

"multibanco":{"entity":"11249","reference":"123 456 789",
              "amount":4990,"expires_at":"2026-07-19T14:05:11Z"}
Seu dever de exibição: mostre entidade, referência e valor ao cliente (e o prazo). Ele paga no homebanking ou numa caixa Multibanco. awaiting_payment é um estado normal que pode durar dias — a confirmação chega pelo webhook order.paid. Não trate como erro nem crie um pedido novo.

Ciclo de vida do pedido

MétodoTransições
MB WAYpending → paid · failed · expired
Multibancoawaiting_payment → paid · failed · expired (voucher venceu)
Qualquerpaid → refunded (somente no estorno total)

Os estados finais não regridem. Um evento duplicado nunca re-transiciona um pedido.

Idempotência

O header Idempotency-Key é obrigatório na criação de pedidos e é a sua proteção contra cobrança dupla em timeouts/reenvios:

  • Mesma chave + mesmo corpo → devolve a resposta original (header Idempotent-Replay: true), sem criar nada.
  • Mesma chave + corpo diferente → 409 idempotency_key_reused. A chave identifica uma tentativa com um corpo exato: mudou o valor/método/telefone? Gere chave nova ("pedido-1042-v2").
  • Retry após failed/expired: é pedido NOVO — external_reference nova (a antiga fica ocupada) E chave nova. Repetir a mesma chave devolve o pedido morto via replay. Exceção: após 402 pode reusar ambas.
  • Só o sucesso fica gravado: se a criação falhou, pode reusar a mesma chave no retry. Retenção garantida: ≥ 24 h.

Use uma chave derivada do seu pedido (ex.: pedido-1042-v1). A external_reference é uma segunda barreira: é única por conta (409 external_reference_taken).

Estornos

curl https://api.broski.pt/v1/orders/ord_9f2c1ab34d/refunds \
  -H "Authorization: Bearer sk_live_..." -H "Content-Type: application/json" \
  -H "Idempotency-Key: estorno-1042-v1" \
  -d '{"amount":500,"reason":"troca"}'   # omita amount p/ estorno total

O corpo JSON é obrigatório: envie {} para estorno total do restante. O header Idempotency-Key (1–128) é obrigatório e é a sua proteção contra estorno duplo: um reenvio com a mesma chave (após timeout, fila que reprocessa, duplo-clique) devolve o estorno original em vez de estornar de novo. Para um segundo estorno intencional, use uma chave nova. Só pedidos paid podem ser estornados (409 order_not_paid); parciais são repetíveis até o total (400 refund_exceeds_amount acima disso). No estorno total o pedido vira refunded e o webhook order.refunded é emitido. O valor devolvido ao cliente segue o caminho do método original.

Webhooks

Essenciais no Multibanco (o pagamento chega dias depois). Cadastre a URL HTTPS no painel (Configurações → Webhooks) e guarde o segredo whbroski_… (também consultável depois em “Ver segredo”). Política de retries na referência.

O corpo é um envelope {id, type, created, data.object} — data.object é o mesmo objeto do GET. Exemplo real de order.paid (ilustrativo, não assinado; a ordem das chaves não importa):

Verificando a assinatura

Header Broski-Signature: t=<unix>,v1=<hex>, onde v1 = HMAC-SHA256(secret, t + "." + corpo_cru). Use o corpo cru (antes de parsear o JSON) e comparação em tempo constante; rejeite t a mais de 5 min do seu relógio.

Node.js
const crypto = require("crypto");
function verificar(sigHeader, corpoCru, secret) {
  const m = /^t=(\d+),v1=([0-9a-f]{64})$/.exec(sigHeader || "");
  if (!m) return false;
  const [_, t, v1] = m;
  if (Math.abs(Date.now()/1000 - Number(t)) > 300) return false;
  const esperado = crypto.createHmac("sha256", secret)
    .update(t + "." + corpoCru).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(v1), Buffer.from(esperado));
}
PHP
function verificar(string $sig, string $corpoCru, string $secret): bool {
  if (!preg_match('/^t=(\d+),v1=([0-9a-f]{64})$/', $sig, $m)) return false;
  if (abs(time() - (int)$m[1]) > 300) return false;
  $esperado = hash_hmac('sha256', $m[1] . '.' . $corpoCru, $secret);
  return hash_equals($esperado, $m[2]);
}
Python
import hmac, hashlib, time, re
def verificar(sig: str, corpo_cru: bytes, secret: str) -> bool:
    m = re.fullmatch(r"t=(\d+),v1=([0-9a-f]{64})", sig or "")
    if not m or abs(time.time() - int(m[1])) > 300: return False
    esperado = hmac.new(secret.encode(), f"{m[1]}.".encode() + corpo_cru,
                        hashlib.sha256).hexdigest()
    return hmac.compare_digest(esperado, m[2])

Vetor de teste

Sua implementação deve reproduzir exatamente este resultado:

secret : whbroski_vetor_de_teste_nao_usar_em_producao
t      : 1750000000
corpo  : {"id":"evt_teste123","type":"order.paid","created":1750000000,"data":{"object":{"id":"ord_teste123","status":"paid"}}}
header : t=1750000000,v1=5fb448226598b14dea45ff94ee317c2c1edd464f87cd720b0d8673ea89731d4c

Node/Express: use app.post("/webhook", express.raw({type:"*/*"}), handler) — express.json() consumiria o corpo cru e a assinatura nunca bateria.

Boas práticas: responda 2xx em ≤10 s (enfileire o processamento); deduplique pelo id do evento (entrega at-least-once, sem ordem garantida); ignore com 2xx qualquer type que não tratar; consulte o log de entregas e o reenvio manual no painel quando algo falhar.

Erros e limites

Envelope único: {"error":{"type","code","message","param?","retry_after_seconds?"}} — catálogo completo na referência. Limites: 120 requisições/min por chave (acima → 429; recue com backoff exponencial), corpo até 64 KB, listagem em páginas de 25 com cursor starting_after.

Bloqueio por telemóvel (MB WAY)

Um telemóvel, um pedido MB WAY de cada vez. Enquanto um pedido MB WAY está à espera de confirmação no app do cliente, o mesmo número não consegue iniciar outro — em nenhuma loja da Broski. A tentativa devolve 409 mbway_pending_for_phone com retry_after_seconds (e o header Retry-After) e uma message já escrita para o cliente final:

{"error":{"type":"conflict","code":"mbway_pending_for_phone",
 "message":"Já existe um pagamento MB WAY à espera de confirmação para este número de telemóvel. Abra o app MB WAY e confirme (ou recuse) esse pagamento antes de iniciar outro. Se preferir, aguarde 4 minutos e tente de novo.",
 "retry_after_seconds":240}}
No seu checkout: mostre a message tal e qual e não trate como falha de pagamento. Nada foi criado (nem na Broski nem na rede MB WAY) — pode reenviar exatamente o mesmo pedido (mesma external_reference e Idempotency-Key) depois de retry_after_seconds. O bloqueio cai no instante em que o cliente confirma ou recusa o push no app, ou expira em no máximo ~5 minutos. Porquê: dois pushes vivos para o mesmo número faziam o cliente pagar um e ver o outro "recusado" — ou pagar os dois.

Recebimentos

Cada venda confirmada entra no seu saldo (painel → Saldo) e passa por um breve período de retenção antes de ficar disponível. O saque para o seu IBAN é pedido no painel (Saques) e passa por revisão. Extrato completo, taxas aplicadas e comprovantes: tudo no painel.

Ambientes e testes

A API opera hoje em produção — o campo livemode nas respostas identifica o ambiente e já prepara a sua integração para o modo de teste sem breaking change.

Como testar com segurança hoje:

  • Crie um pedido MB WAY de 50 (€0,50 — o mínimo real) para o seu próprio telemóvel, confirme, e verifique o webhook order.paid; depois estorne via API.
  • Valide a sua verificação de assinatura contra o vetor de teste antes de ir ao ar.
  • Acompanhe entregas de webhook (e reenvie manualmente) no painel.

O modo de teste com chaves sk_test_ está em desenvolvimento e será anunciado no changelog.

Checklist de produção

  1. Conta verificada e ativa no painel.
  2. Chave sk_live_ guardada só no servidor (variável de ambiente/secret manager).
  3. Idempotency-Key derivada do seu pedido em toda criação.
  4. Voucher Multibanco exibido com entidade, referência, valor e prazo.
  5. Webhook HTTPS cadastrado; assinatura verificada (vetor de teste passa); dedupe por id; resposta 2xx ≤ 10 s.
  6. Liberação do produto somente no order.paid (nunca na criação).
  7. Tratamento de 429 com backoff e de 402/expired/failed com mensagem clara ao cliente.
